# intent — #69 순서 제안 실경로 연결

`docs/intent.md` 의 "9/20 자정까지 반드시 동작해야 하는 것" 중 **D3(사진 3~20장 → 1~N 순서 + 자리마다 근거)** 와
**D6(같은 사진 + 다른 프로필 2벌 → 다른 결과 2벌)**, 그리고 그 둘을 떠받치는 **S3(프로필이 결과를 실제로 바꾼다)** 를 향한다.

## 왜 이 이슈가 필요한가

이 제품의 1순위 차별점은 "사진 순서를 정해준다" 다. 그런데 **실제 HTTP 경로에서 그 기능이 켜지지 않는 조건이 남아 있다.**
`lib/order.js` 의 `orderFeed` 는 이미 만들어져 있고 #12·#41 에서 실사진 20장으로 검증까지 끝났는데,
`lib/pipeline.js` 가 그것을 **부르지 않고 우회하는 분기**를 아직 들고 있다.

이슈 본문은 "pipeline 이 preserveOrder 를 쓴다" 라고 적고 있지만, 코드를 읽어 보면 정확히는 **조건부**다:

```js
// lib/pipeline.js — 변경 전
target.kind==='photo_plan' || photos.some(p=>p.analysis_source==='heuristic')
  ? preserveOrder(...) : composeFeed(...)   // composeFeed → orderFeed
```

즉 `orderFeed` 는 이미 연결돼 있고, **두 개의 우회 조건 중 하나라도 걸리면 큐레이션이 통째로 꺼진다.**
그래서 이 이슈의 본질은 "연결하기" 가 아니라 **"두 우회 조건이 아직 근거가 있는지 하나씩 판정하기"** 다.
이것이 이슈가 "`preserveOrder` 를 그냥 지우지 마라" 라고 못 박은 이유이기도 하다.

## 무엇이 되면 끝인가

1. **근거가 사라진 우회 조건은 없앤다.** `analysis_source==='heuristic'` 이 그것이다 —
   `test/order.real20.json` 20장이 전부 휴리스틱 분석 결과이고 #41 이 바로 그 입력으로 `orderFeed` 를 검증했다.
   레포 안에 이미 "휴리스틱 입력에서도 `orderFeed` 가 동작한다" 는 증거가 있는데도 실경로에서만 꺼져 있다.
2. **근거가 남아 있는 우회 조건은 남기되, 왜 남는지를 코드에 적는다.** `photo_plan` 이 그것이다 —
   `orderFeed` 는 `validateProfile(target,'target')` 을 부르는데 `planFromPhotos` 의 산출물은 TargetProfile 이 아니다.
   이것은 "아직 안 고침" 이 아니라 **스키마가 그렇게 정한 것**이므로 분기로 남는 게 맞다.
3. **우회를 걷어낸 결과가 실제로 D3·D6 을 만족하는지 실행으로 본다.** 코드가 바뀌었다는 것과
   `POST /api/feed` 에 사진 15장을 넣었을 때 입력과 다른 순서가 나온다는 것은 다른 주장이다. 후자를 출력으로 남긴다.
4. **켜지지 않는 것이 하나 더 있다는 사실을 숨기지 않는다.** R1 동점 타이브레이크(`resolveTiebreak`)는
   `target.visual.palette` 를 요구하는데 TargetProfile 을 만드는 두 경로가 그것을 채우지 않는다.
   이 이슈의 DoD 는 그것을 **고치라**가 아니라 **기록하라**다. 고쳐야 할 것과 알고 있는 것을 구분해서 남긴다.

## 이 이슈가 끝나도 안 되는 것

- `photo_plan`(사진만 입력) 경로의 순서는 여전히 입력 순서다. 그 경로에는 지향이 없어 방향을 정할 근거가 없다.
- `visual.palette` 미충족은 이 이슈에서 고치지 않는다. 별도 이슈 후보로 남긴다.
