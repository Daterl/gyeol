# 왜 이 이슈가 필요한가 — 보정축이 순서에 닿게 한다

## 무엇이 깨져 있나

`CurrentProfile`(보정축)을 무엇으로 바꿔도 `position` 으로 정렬한 `photo_id` 배열이 한 자리도
달라지지 않는다. `lib/order.js` 의 `orderFeed` 가 `currentProfile` 을 받기는 하지만
검증(`validateProfile`)과 ID 스탬프 두 곳에서만 쓴다.

## 왜 그게 심각한가 — 기능 결손이 아니라 제품 정의 위반이다

`pivot/docs/20-product-definition.md` 가 스스로 적어 둔 실패 조건에 그대로 걸린다.

- **W4 (2순위 차별점)** — *"스타일 프리셋·필터·템플릿은 전부 입력이 같으면 출력이 같은 물건이라
  원리적으로 이 문장을 쓸 수 없다."* 지금 출력이 정확히 그 상태다. 지향만 같으면 누가 써도 같은 순서가 나온다.
- **F1-6 R1** — *"지향만 반영하면 제품이 스타일 프리셋 적용기로 전락한다. 보정축이 이 리스크의 해답이다."*
- **V3 (무대 증명 장면)** — *"같은 레퍼런스 + 같은 사진, 두 사람 → 다른 결과"* 를 **현재 코드로는 만들 수 없다.**

즉 데모에서 "다른 계정을 넣어도 같은 결과 아닌가요" 라는 질문에 코드로 답할 수 없다. `S3`(프로필이
결과를 바꾼다)가 절반만 성립한다.

## 무엇이 되면 끝인가 — 그리고 왜 그 조건인가

1. **보정축만 다른 두 세션이 서로 다른 `photo_id` 배열을 낸다.**
   `slots[].position` 은 언제나 `[1..N]` 이라 대조에 쓸 수 없다. 실제로 무엇이 바뀌었는지 말하는 값은
   "몇 번 자리에 어느 사진이 갔는가" 하나뿐이므로 **`position` 으로 정렬한 `photo_id` 배열**을 증거로 남긴다.
2. **보정축이 비어 있으면(`present:false`) 수정 전과 완전히 같은 결과가 나온다.**
   이 조건이 1번보다 중요하다. `#9`·`#12`·`#41`·`#69`·`#96` 이 전부 같은 형태로 무너졌다 —
   **관측되지 않은 값이 판단을 바꾸는데 근거에는 나타나지 않는다.** 없는 축이 기본값으로 순서를 움직이면
   그게 여섯 번째다. 그래서 "차이를 만든다" 가 아니라 "관측된 차이만 반영한다" 가 완료 조건이다.
3. **순서가 바뀐 이유가 근거 문장에 드러난다(P2).**
   보정축이 방향을 바꿨는데 사용자에게 보이는 문장이 "지향 점수가 가장 높아서" 라고만 말하면,
   차이는 생겼지만 근거를 못 대는 판단이 된다. 그건 고친 게 아니다.
4. **회귀 테스트가 이 셋을 고정한다.** 되돌리면 실패해야 증명이 유지된다.

## 범위를 어디서 끊는가

이슈가 "범위를 늘리지 않는 선택도 유효하다" 고 명시했다. 시각축까지 합성하려면 `applied_profile.visual`
과 간극 카드(`deltas`)를 함께 늘려야 하고 그건 `#13` 소관이다. **이번 작업은 두 축이 이미 둘 다 실측하고
있고 이미 합성까지 끝나 있는 필드 하나 — `language.caption_len` — 를 순서 판단이 실제로 읽게 만드는 데서
끊는다.** 남는 간극은 `spec.md` 5절과 PR 본문에 적는다.
