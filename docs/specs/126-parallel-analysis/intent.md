# #126 — 사진 분석 병렬화 · 왜 하는가

## 왜 이 이슈가 필요한가

`docs/intent.md` 4-3 절의 **D2 는 "30초 안에 결과"** 를 요구한다. D3 는 "내 사진 3~20장 업로드 → 1~N 순서" 다.
지금 `src/features/input/input.ts` 의 `upload()` 는 `for` 루프 안에서 `await analyzePhoto(...)` 를 돈다 — 한 장씩 순서대로다.

이 워크트리에서 실사진 15장을 `POST /api/analyze` 로 올려 재측정한 결과 **155.0초**(2분 35초)다.
이슈 #126 이 보고한 167초와 같은 자릿수다. 장당 8.8~19.2초, 최대 19.2초.

## 왜 그 DoD 인가

- **30초는 UI 목표가 아니라 이탈 경계다.** 온라인 투표에서 투표자가 2분 35초를 기다리지 않는다.
  진행률 UI 를 붙여서 기다리게 만드는 것은 P3(다 채우지 않는다)이 막았고, 애초에 문제는 대기의 길이다.
- **동시 실행 수 상한이 DoD 인 이유:** 15개를 한꺼번에 던지면 429(rate limit — 제공자가 분당 요청/토큰을 제한하는 응답)를
  맞는다. 429 를 맞으면 병렬화가 오히려 느려지고 실패한다. 상한값은 추측이 아니라 실측으로 정해야 근거가 된다(P2).
- **한 장 실패가 15장 전체를 죽이지 않아야 하는 이유:** 실측 최대 19.2초는 `lib/model.js` 의 `MODEL_TIMEOUT_MS = 20_000`
  에 0.8초밖에 여유가 없다. 병렬화하면 한 장의 지연이 전체 대기에 더해지지 않는 대신, **한 장이 죽을 확률은 그대로다.**
  지금은 `photos.every((p,i)=>p.input_index===i)`(`lib/interaction.js:26`) 때문에 한 장이 빠지면 `input_index` 가 끊겨
  `POST /api/feed` 가 400 을 낸다. 병렬화만 하고 이걸 두면 "빠르게 실패하는 제품"이 된다.

## 무엇이 되면 끝인가

1. 실사진 15장 분석이 30초 안에 끝난다. 못 맞추면 실제 시간과 남는 병목을 그대로 적는다.
2. 한 장이 실패해도 나머지로 `POST /api/feed` 가 200 을 낸다.
3. 동시 실행 상한이 있고, 그 값을 고른 실측 근거가 `report.md` 에 있다.
4. 사진 한 장당 한 번 호출하는 구조는 그대로다(작업 규약). 여러 장을 한 호출에 몰지 않는다.
