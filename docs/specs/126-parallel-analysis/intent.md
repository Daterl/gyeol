# #126 — 사진 분석 병렬화 · 왜 하는가

## 왜 이 이슈가 필요한가

`docs/intent.md` 4-3 절의 **D2 는 "30초 안에 결과"** 를 요구한다. 현행 D3 입력은 사진 3~15장이다.
수정 전 `src/features/input/input.ts`의 `upload()`는 한 장씩 순서대로 분석했다. 현행 구현은 동시 실행을 8개로 제한한다.

이 워크트리에서 실사진 15장을 `POST /api/analyze` 로 올려 재측정한 결과 **155.0초**(2분 35초)다.
이슈 #126 이 보고한 167초와 같은 자릿수다. 장당 8.8~19.2초, 최대 19.2초.

## 왜 그 DoD 인가

- **30초는 UI 목표가 아니라 이탈 경계다.** 온라인 투표에서 투표자가 2분 35초를 기다리지 않는다.
  진행률 UI 를 붙여서 기다리게 만드는 것은 P3(다 채우지 않는다)이 막았고, 애초에 문제는 대기의 길이다.
- **동시 실행 수 상한이 DoD 인 이유:** 제한 없이 요청하면 제공자 대기와 브라우저 메모리가 커질 수 있다.
  실측에서는 동시 5·8·15 모두 429가 없었지만, 15는 장당 지연과 메모리 부담이 커 8을 선택했다.
- **한 장 실패를 숨기지 않아야 하는 이유:** 실측 최대 19.2초는 `lib/model.js` 의 `MODEL_TIMEOUT_MS = 20_000`
  에 0.8초밖에 여유가 없다. 한 장이 끝내 실패하면 실패 파일을 알리고, 사용자가 재시도하거나 삭제하기 전에는
  `POST /api/feed`를 호출하지 않는다.

## 무엇이 되면 끝인가

1. 실사진 15장 분석이 30초 안에 끝난다. 못 맞추면 실제 시간과 남는 병목을 그대로 적는다.
2. 한 장이 실패하면 파일을 알리고, 사용자가 재시도하거나 삭제한 선택으로 다시 제출할 때만 `POST /api/feed`가 200을 낸다.
3. 동시 실행 상한이 있고, 그 값을 고른 실측 근거가 `report.md` 에 있다.
4. 사진 한 장당 한 번 호출하는 구조는 그대로다(작업 규약). 여러 장을 한 호출에 몰지 않는다.
